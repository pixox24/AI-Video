## 3. 必须修复的问题

### G01 — P1：requestId 未贯穿路由，合法重编可能被误拒绝

关联：S01、S02、S11；原 F01/F08、T27。

位置：`server.ts:1952`；`src/services/visualBibleService.ts:76`、`:230`；`src/components/ScriptPanel.tsx:506`、`:524`、`:757`。

实际流程：

1. UI 生成 `vb-时间-随机串` 并放进请求体。
2. 路由没有取出和传递这个 requestId，领域服务另生成 `vb-时间`。
3. 接收函数只有在“requestId 不同，且当前/返回的 bibleRevision 也不同”时才拒绝。
4. 对已有圣经的有效重编，约束发生变化意味着结果版本应变化；此时恰好满足拒绝条件。UI 返回旧 base，外层却继续显示重编完成状态。

S01 证明真实路由没有原样返回客户端 ID。S02 以同一文案、上一版不同色板为输入，生产函数正常返回新版本，但实际接收函数拒绝该有效结果。

反方向也有漏洞：当 ID 不同但结果版本相同，旧请求仍被接受（S11）。此外，UI 校验参数来自发起请求时的 `base` 和文案闭包，没有读取用户操作后的最新状态。辅助函数有调用方，并不等于竞态防护已经有效。

修复方案：

- UI → 路由 → 服务 → 响应原样贯穿 requestId；为当前活动请求保存可核验标识。
- 将“请求是否仍有效”与“结果版本是否变化”分开。不能用结果版本相等来允许未知旧请求，也不能用结果变化来拒绝当前有效请求。
- 请求时记录 sourceKey、目标项目和用户状态版本；响应时读取最新状态进行判断，并有条件合并。
- 请求被废弃时返回明确状态，不走“重编成功”提示和旧 base 覆盖流程。
- 增加正常重编、两请求乱序、请求中改稿、同稿改锁、同结果旧请求等生产接入测试。

验收：S01、S02、S11 通过，T27 覆盖实际接收和提交代码。

### G02 — P1：只编辑一个外形字段，会清空其他字段

关联：S03；原 F02/F04、T26。

位置：`src/utils/visualBible.ts:1908`、`:1920`；`src/utils/visualBibleState.ts:154`、`:167`。

`updateCharacterField` 总是构造包含 look、wardrobe、ageBand、signature 四个键的 patch，即使调用者只提供 look。未提供的键值是 undefined。reducer 对卡面直接执行 `{ ...item, ...action.patch }`，因此覆盖掉原服装、年龄、标志特征。

S03：原卡服装为“蓝色校服”、特征为“圆框眼镜”，只修改 look 后，卡面的 wardrobe 等变成 undefined。override 内部使用 `??` 保留了旧值，但展示卡没有使用同一个处理规则，产生事实上的双份不一致状态。由于 UI 不再每次 ground，不能指望下一次 ground 自动修复当前操作。

修复方案：只传实际修改的键；或在 reducer 逐字段应用并忽略未提供值。明确“未提供”和“用户主动清空”的区别，不能用 `||` 把主动清空误当作缺省。所有派生字段由同一提交过程生成，再计算最终结果版本。

验收：分别编辑四个字段，验证另外三个原样保留；主动清空可保存；重载后状态和版本一致。S03 通过。

### G03 — P1：显示名保存了，但改名导致角色从分镜中消失

关联：S04；原 F04/F06。

位置：`src/utils/visualBible.ts:1139`、`:1462`、`:1497`。

ground 现在允许显示名不同于台账规范名，但 `charactersMentionedInLine` 仍只执行 `text.includes(character.name)`。

S04：王小明显示名改成“小明同学”，ground 后卡名确实保留；接着处理“王小明走进教室。”，自动上镜列表却变成空数组。原 R05 只验证卡面名称，没有验证名称变化后的下游身份识别，因此无法发现此问题。

修复方案：上镜和证据匹配以 entityId、规范名、经验证的别名/mention 为依据；显示名只用于展示和必要的提示词称呼。不要让 UI 改名重定义原文身份。

验收：改显示名 → 原文点名 → 代词延续 → 提示词 → 保存重载，仍指向原实体；S04 通过。

### G04 — P1：参考图写回仍能覆盖新图，或装到另一实体上

关联：S08、S09；原 F08、T27。

位置：`src/App.tsx:930`、`:933`、`:940`。

本轮改用 `setProject(prev => ...)`，解决了整份旧 workspace 写回的一部分问题，但仍缺少目标身份和请求版本判断。

- S08：旧参考图生成中，用户已上传新参考图；旧生成完成后，实际 updater 仍覆盖用户刚上传的新图。
- S09：旧图对应王小明，当前卡是李小红但复用了旧卡 ID；updater 优先按 cardId 找到李小红，没有核对 entityId，就写入王小明的图。该检查针对卡 ID 复用/旧工程兼容条件，不声称所有新卡都会使用相同 ID。

修复方案：发起时记录项目 ID、entityId、当前参考图版本、外形版本和请求 ID；回写时全部按需要核验。卡 ID 相同不能证明实体相同。用户已经上传、清除、换图、改外形、删除角色或切项目时，旧结果不能继续作为当前图写入。

验收：S08、S09 通过；还需对上传文件的异步完成路径做同类验证。

### G05 — P2：版本化缓存存在绕过路径，切模型仍复用旧分析

关联：S05；原 F01、T11/T28。

位置：`src/services/visualBibleService.ts:82`、`:99`、`:112`；`server.ts:1959`。

内存缓存虽然开始使用 analysisCacheKey，但优先分支 `cachedFromPrev` 只核对 provenance 和 sourceKey，不比较存储的 analysisCacheKey。因此，带入上一份圣经时可以绕过模型/解析器/提示词版本失效规则。

S05：模型 A 完成一次分析，模型 B 使用相同文案和 previousBible 再编；B 的实际 analysisCalls 为 0。

生产路由也尚未把 llmApi 中的实际模型标识、语言字段传入服务。只修服务参数，不更新真实调用方，缓存契约仍不会生效。

修复方案：所有缓存入口比较完整键；从 previousBible 恢复时校验分析版本并保存完整已验证分析快照，避免把 `entities: []` 的重建对象当成完整分析。使用统一的规范化 AnalysisInput 构造 sourceKey 和 analysisCacheKey，确保语言与规范化文本一致。

验收：S05 通过；模型、提示词、解析器、语言切换分别验证失效；同输入同版本验证命中。

### G06 — P2：接入领域服务时丢失正式编卡的风格约束

关联：S06；原 F01 中“接入时保留正式提示词”要求。

位置：`src/services/visualBibleService.ts:175`；`server.ts:1959`。

路由传入 stylePack，但服务从未将其用于正式编卡提示词。S06 使用合法 presetStylePack 并设置明确标签，生产路由最终送给编卡模型的 prompt 没有此约束。

同时，正式编卡模板相比原路由大幅缩短，没有完整的输出 JSON 字段示例和 refs/locked 等原有约束。即便后续图像提示词仍有风格，圣经中的场景、服饰和色板分析也已失去先前输入。

修复方案：恢复并集中维护正式编卡契约，显式包含经过规范化的世界、服饰、空间、色板等风格约束，以及输出 schema、实体 ID 关系、证据、未知外形和参考图字段要求。分析缓存与设计编译缓存分别管理。

验收：S06 通过；同文案不同合法风格包，实际编卡请求应体现差异；不以模拟模型固定返回值代替 prompt 契约测试。

### G07 — P1：性别不匹配时仍回退到错误人物

关联：S07；原 F06、T21/T22。

位置：`src/utils/visualBible.ts:1542`、`:1546`。

新增性别过滤只在筛出至少一个人物时才替换 prevMentioned；若上一句只有不匹配的女性，筛选为空，代码仍返回这名女性。

S07 使用明确男孩/女孩的两张卡：“王小明走进教室。李小红坐下。他打开课本。”最后一句被关联到李小红。角色身份已明确，这不是合理的未知性别歧义。

修复方案：与明确性别或数量冲突的候选不得回退为有效主体。继续寻找合法上下文；无法确定时保留歧义诊断，而非绑定已知错误的人。逐步落实句级 mention/event，避免不断添加只覆盖特定词面的分支。

验收：S07 通过；增加相反性别、两名同性、多人复数、跨段和无可解析对象的场景。

### G08 — P2：恢复 auto 没有恢复分析事实和派生状态

关联：S10；原 F04、优化方案 include/exclude/auto 契约。

位置：`src/utils/visualBibleState.ts:52`、`:96`。

确认角色时直接把 ledger 状态改成 confirmed；恢复 auto 时只更新 override，原分析 pending 状态已经没有在该台账中保留，卡面也没有重新派生。

S10：匿名女孩原为 pending，用户确认后恢复 auto，仍然留在 active confirmed。此项针对已有 reducer 的公开动作和原方案契约，不把尚未完整提供的 UI 入口描述为已经做过浏览器测试。

修复方案：分析事实不可被用户决定原地替代，保留基础事实快照；任何 include/exclude/auto 变化都从基础事实与当前 override 派生新状态。恢复 auto 后按原事实回到 pending/自动纳入/排除。

验收：S10 通过；覆盖 include→auto、exclude→auto、重复切换、保存重载，不得依赖重新调用模型才能恢复。
