## 3. 阻止验收通过的具体问题

### F01 — P1：生产 API 与被测试的领域服务分离，降级分析会被错误缓存

位置：`server.ts:1951`、`server.ts:1978`；`src/services/visualBibleService.ts:65`；原审计脚本的服务导入。

实际 `/api/script/visual-bible` 路由仍自己执行分析、编卡、合并、ground 和 stamp，没有调用 `compileVisualBible`。因此，领域服务中的缓存、请求标识等实现不能直接证明界面实际请求具备相同能力。原审计已经改成调用新服务，失去了对真实路由差异的覆盖。

生产路由只要发现相同来源键的 `entityLedger` 就跳过模型分析，没有区分正式成功分析与规则降级台账。复现：先用规则生成“我走进房间，然后我看向窗外。”的台账，随后配置可用模型并重编；实际只调用编卡一次，未重新做应执行的整篇分析。对应 R01、R11。

`analysisCacheKey()` 虽已定义，但实际缓存接入仍使用 `sourceKey`；模型、解析器、提示词版本未成为真正的缓存失效条件。语言字段也尚未贯穿真实请求构造。

修复要求：

1. 路由必须委托同一领域服务，保留实际风格约束、台账约束、模型配置与正式编卡提示词；不能直接拿服务目前的占位 `system: 'visual-bible'` 替换正式提示词。
2. 服务统一持有分析输入、完整已验证分析快照、分析版本、缓存键及 provenance。
3. 规则降级、失败和损坏缓存不得阻止后续正式分析；提供明确的强制重分析语义并接入真实路由。
4. 同时验证服务单测和薄路由契约，包括模型调用次数、模型版本切换、语言切换、异常降级。

通过条件：R01、R11 通过；生产路由与服务输出契约一致；T11、T28 等失败恢复测试落实。

### F02 — P1：改外形和换参考图没有更新结果版本，旧提示词仍可复用

位置：`src/utils/visualBible.ts:1785`、`:1843`；`src/components/ScriptPanel.tsx:2445`；`src/utils/imagePrompt.ts:268`；`src/utils/visualBibleSource.ts:72`。

UI 的 `patchBible` 已经不再 ground，但没有增加统一的版本更新动作。`updateCharacterField`、`setCharacterRef`、确认/拒绝等路径直接改卡或 override，通常保留旧 `bibleRevision`。`rebuildForecast` 也不更新该版本。

R02 按真实函数组合执行：生成圣经 → 改角色外形 → `rebuildForecast` → `compileImagePrompt`。当旧提示词已 pinned 且旧 hash 匹配时，编译器直接返回旧提示词，角色新外形没有进入请求。

另有两类接入不完整：

- `App.tsx:1048`、`:1186`、`:1299`、`:1362` 和 `StoryboardPanel.tsx:163`、`:204`、`:370` 等写入点仍写 `sourceHash`，读取端却比较 `bibleRevision`。新提示词也可能被立即当作过期，造成反复重算或失去手动提示词。
- 版本计算只取场景名称，未覆盖场景外观、时间等实际提示词约束；即使补上调用，也要先明确完整的版本输入。

修复要求：统一状态提交后计算结果版本；所有提示词写入和读取使用同一版本定义。用户改外形、服装、参考图、角色选择、场景约束均应使相关提示词失效，原文未变时不应让分析缓存失效。

通过条件：R02、T26 覆盖真实更新入口并通过；分别断言旧提示词失效、重编后的提示词可复用、sourceKey 不变、analysisCache 不误失效。

### F03 — P1：三把锁的状态仍会互相覆盖

位置：`src/utils/visualBibleState.ts:166`、`:185`；`src/utils/visualBible.ts:1843`；`src/utils/visualBibleMigration.ts`。

`setCharacterRef` 给卡面写入 `refsLocked=true`，但不更新 override 中的锁。随后 `set_entity_lock` 从 override 或全 false 的 `emptyOverride` 构造全部三锁，再覆盖卡面。实际结果：上传参考图后，点击身份锁，参考图锁被变为 false（R03）。

迁移后已有 `appearanceLocked=true`、但没有 override 的旧卡，也会在首次切换身份锁时丢失外形锁（R04）。这说明“一次性布尔锁迁移”只解决字段兼容，没有完成整份用户状态迁移。

修复要求：

1. 迁移时同步建立 override，保留三把锁的独立值。
2. 上传/生成/移除参考图全部走统一 reducer，参考图及其锁只有一个权威位置。
3. 切换一把锁只能改这一把，禁止用缺省值重写其他锁。
4. 测试所有八种锁组合，并覆盖上传图后切锁、清图后切锁、迁移后切锁、重编和重载。

通过条件：R03、R04 通过，且 T18 不再只测试 `migrateLockFlags` 单函数。

### F04 — P1：用户显示名和 include 尚未贯穿统一状态流

位置：`src/utils/visualBible.ts:1785`、`:1138`；`src/utils/visualBibleState.ts:137` 附近；`src/components/ScriptPanel.tsx:2639`。

已新增的 `set_entity_display_name`、`set_entity_appearance` 未被真实编辑入口统一采用；`updateCharacterField` 仍直接改展示数组。把王小明显示名改为“小明同学”后再校验，会被当作实体错配而恢复原名（R05）。

`applyAnalysisToBible` 又独立重建台账和 allowed/pending，没有应用 `bible.overrides`。已确认匿名女孩，再经过这层分析投影后角色消失（R10）。该检查证明中间权威层不满足用户决定不变量；并不把它夸大成每条最终 UI 路径都必然丢失，因为后续 ground 在部分路径可能再次修回。

修复要求：事实身份与显示名分开；确认、拒绝、恢复自动、改显示名、改外形都由统一动作生成派生状态。分析只能更新事实快照，所有派生必须重新应用当前用户决定；不要靠随后另一次 ground 补救。

通过条件：R05、R10 通过，并用“操作 → 请求 → 服务投影 → 接收 → 保存 → 重载”链路验证 include/exclude/auto 和用户字段。

### F05 — P1：pinned 旧快照在换稿重载时被盖上新来源

位置：`src/utils/scriptWorkspace.ts:203`；`src/utils/visualBible.ts:1072`、`:1272`；`server.ts:2041`。

当圣经来源与当前稿件不同，`normalizeScriptWorkspace` 会调用 ground。ground 无条件把来源字段改成当前文本的键，pinned 状态并未阻止这一操作。

R09：钉住王小明稿件的圣经，当前口播改为李小红，重载工程后 `sourceKey` 已变成新稿的键。旧快照来源差异不再可靠，违背 T30 的明确要求。

修复要求：pinned 保存冻结快照的来源；另行计算“当前文案与快照不同”的状态。重载只做迁移和恢复，不能把重新校验等同于用户同意重编。API 的 stamp 也必须遵守该规则。

通过条件：R09、T30 在前端加载、API 返回和保存重载三处均通过。

### F06 — P1：代词处理仍是局部中文回溯，不能支撑稳定的多人分镜

位置：`src/utils/visualBible.ts:1430` 附近的 `pronounSubject` 分支。

已确认的不同失败情形：

| 输入/前提 | 应有结果 | 实际结果 | 检查 |
|---|---|---|---|
| 已有王小明、李小红两卡；前句“男孩王小明与女孩李小红走进教室”，后句“她打开课本” | 后句关联李小红 | 把上一句两个人都赋给“她” | R06 |
| “王小明走进教室。他看向窗外。” | 第二句是人物动作镜 | 因“窗外”关键词排除代词分支，变成无人 | R07 |
| 已有 John 卡；“John enters the room. He opens the book.” | 第二句关联 John | 英文 He 未被识别 | R08 |

R06、R08 使用已建立角色卡来隔离上镜算法，不把抽取能力与上镜能力混成一个断言。

修复要求：按句保存 mention/event 及可复核共指关系；根据行动者、说话者、性别/数量和上下文确定主体。无法确定时输出可诊断歧义，不把前一句所有人当成当前主体。区分“人物看树”与“树的空镜”，中英文能力均应有明确契约。

通过条件：R06–R08 通过；T21–T25 有完整测试；真实可解析共指动作的主体集合准确率达到方案门槛。

### F08 — P1：异步旧响应覆盖保护没有接入真实用户操作

位置：`src/components/ScriptPanel.tsx:496`、`:744`、`:2453`；`src/App.tsx:930`、`:937`；`src/services/visualBibleService.ts:202`。

代码审查发现：生成参考图结束后，使用请求发起时捕获的 `bible` 和 `workspace` 写回整个工作区；重编和上传图也有同类闭包。期间修改外形、切锁、改文案或切换对象时，完成的旧请求可能覆盖新状态。

新增 `receiveVisualBibleResponse` 没有调用方，且自身只比较来源键，没有比较 requestId/用户状态版本；文案不变但用户锁或参考图已变化时，仅比 sourceKey 不够。

这是静态调用链审查发现的高可信风险，**本轮没有把未做的浏览器竞态实验记为已经动态复现**。

修复要求：捕获 requestId、sourceKey、目标 entityId 和需要保护的用户版本；完成时读取最新状态并条件合并，只写仍有效的目标字段，不覆盖旧整份 workspace。给测试显式延迟控制，覆盖“请求中改文案”“同稿改锁”“角色删除后旧图返回”等顺序。

通过条件：T27 在真实接收函数和 UI 接入层通过；不能只增加一个未调用的辅助函数。

### F09 — P1：换稿后旧锁定角色仍留在活动角色中

修复要求：先对齐身份再合并字段，失去当前稿件对应关系的用户资产转入 retired，保留引用及决定，提供明确重新关联操作。除非用户主动纳入，不得作为当前自动上镜角色。

通过条件：R13 通过，T19–T20 覆盖 retired 保存、重载和资产回收保护。

## 5. 测试证据为什么不足以支持“已完成”

`visualBible.acceptance.test.ts` 当前定义了 14 个 T 编号测试：T01–T10、T12、T18、T23、T26。测试编号出现不等于该编号在优化方案中的全部断言完成。

最明确的例子是 `src/utils/visualBible.acceptance.test.ts:193`：测试名称写着“改外形后 bibleRevision 变、sourceKey 不变”，但只断言 sourceKey 相等，既未计算/检查结果版本，也没有编译提示词。这个测试可以通过，同时真实旧 pinned prompt 继续被使用。

其他缺口包括：

- T18 未覆盖实际用户动作中的八种锁组合与重载。
- 服务模拟测试不能替代真实 API 路由契约。
- 未按 T11–T32 完整落实手动上镜、乱序响应、资产迁移、容量限制、双人参考图及 pinned 行为。
- `mentions/events` 未成为可复用的句级事实快照；声明 V2 不代表 V2 所需能力已实现。
- 多参考图仍以单张 `characterRef` 为主，必须验证实际请求和 UI 提示一致。原方案允许供应商不支持多图时明确降级，但需要产品行为和对应测试。
